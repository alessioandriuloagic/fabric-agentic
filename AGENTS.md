## Workflow discipline for Fabric Agentic

This section was generated by the `dai-agentic-starter-pack` plugin's
`/init-dai-project` skill. Re-running that skill updates only the content
between the `init-dai-project` markers above and below — everything else
in this file is left untouched.

### Branching

Use **GitHub Flow** for every change, including semantic model (TMDL),
notebook, and pipeline definition changes — treat these exactly like
source code, since Fabric's Git integration diffs and merges them the same
way:

- `main` is always deployable/releasable.
- Create short-lived, descriptively-named feature branches off `main` for
  any change — never commit directly to `main`.
- Open a pull request early, push commits, and merge to `main` via
  reviewed PR (no long-lived release/develop branches).
- Deploy/tag (and promote through Fabric Deployment Pipelines) from `main`
  after merge.

### Development loop

Build features and fixes through this plugin's vendored engineering
skills, one red-green slice at a time:

1. `/implement` drives `/tdd` internally for each concrete piece of
   behavior, rather than writing everything up front untested.
2. Before merging, run `/code-review` — a two-axis review (does it match
   this repo's conventions, does it match what was asked for) of the diff
   against `main`.
3. As part of that same PR, add a `CHANGELOG.md` entry (see below) — do
   not merge a behavior-changing PR without one.
4. Only then open/merge the PR.

### CHANGELOG and releases

Maintain a root `CHANGELOG.md` using the
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format (seeded by
`/init-dai-project` if one didn't already exist), and version this
project with [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

- **Every PR** that changes behavior — application code, a semantic model,
  a notebook, a pipeline definition, or this file itself — adds an entry
  under `## [Unreleased]` before it merges. This is a normal, per-PR step,
  not a release.
- **Cutting an actual release (bumping the version and tagging `main`) is
  a separate, much less frequent action**, done only when a human asks for
  it. There is no fixed trigger-phrase list to pattern-match against —
  treat any human request to release, ship, deploy a version, or
  "rilasciare"/"rilasciamo" a version, in whatever phrasing they use, as
  triggering this protocol.
- **No dedicated persona owns this.** It's a process rule, not a job for
  one specific agent — whichever agent or session is active when the
  human asks handles it directly, following the steps below.
- **Never guess or silently proceed with a version number.** When asked to
  release:
  1. Look at what changed since the last tag and propose a version bump
     using standard semver rules — patch for fixes only, minor for
     backward-compatible additions, major for anything breaking.
  2. State that proposal to the human and **wait for their explicit
     confirmation (or a different number they choose instead)** before
     doing anything else. Do not tag or push based on your own guess.
  3. Once confirmed: promote `## [Unreleased]` to `## [X.Y.Z] - <date>`
     (today's date) and add a fresh empty `## [Unreleased]` above it.
  4. Commit that promotion through the normal GitHub Flow above — open a
     short-lived `chore(release): vX.Y.Z` branch/PR, get it merged, don't
     push straight to `main` even for a release commit.
  5. Tag the merged commit on `main` as `vX.Y.Z`, and, if this project's
     platform supports it, create a Release/note there using the promoted
     CHANGELOG section as its body.

### Domain glossary

Maintain a root `CONTEXT.md` glossary for this project's own Power BI/
Fabric domain vocabulary — table and measure naming, business term
definitions, and any hard-to-reverse modeling decision recorded as an ADR
under `docs/adr/`. Use the `/domain-modeling` skill to keep it sharp as the
model evolves; don't let table/measure names and business terminology
drift out of sync with what's actually in the semantic model.

### Secrets and credentials hygiene

- Never commit connection strings, API keys, tokens, or service principal
  secrets to source control, including inside notebook cells, pipeline
  definitions, or `.mcp.json`-style configuration.
- Treat Fabric workspace IDs, capacity IDs, and environment names as
  ordinary environment-specific configuration, not secrets — but still
  keep them out of hardcoded semantic model/report definitions where a
  parameter or deployment-pipeline rule would do instead.
- Use your platform's secret store (e.g. Key Vault, GitHub Actions
  secrets) for anything credential-shaped, and reference it by name rather
  than value in checked-in files.

### Using this plugin's delivery agents

`dai-agentic-starter-pack` ships a virtual delivery team as Copilot custom
agents. Regenerate this table from the plugin's own `agents/lineup.md` and
each `agents/<name>.agent.md`'s `description` frontmatter whenever this
section is (re-)written, so it never drifts from the actual roster:

| Agent (@name) | Role | Use it for |
|---|---|---|
| `@dave` | HR Manager | Adding a new team member, updating the roster in `lineup.md`, or revising an existing agent's role/skills. |
| `@ada` | Senior Researcher | Investigating skills, tools, and methodologies before hiring a new agent, exploring capabilities for a new task type, or evaluating tools/methodologies for the team. |
| `@karl` | Business Analyst (funzionale) | Starting a new project, running stakeholder workshops, defining KPIs/metrics, or preparing a handoff package for Marco/Reza. |
| `@ralph` | Fabric Solution Architect | Starting a medium/large project with open architectural decisions, choosing between Lakehouse/Warehouse/Eventhouse, defining cross-project standards, sizing capacity, or doing a pre-delivery architecture review. |
| `@marco` | Data Analyst Power BI | Building or reviewing a semantic model, writing/optimizing DAX measures, designing a report or dashboard, troubleshooting Power BI performance, or releasing to Dev/Test/Prod. |
| `@reza` | Data Engineer Fabric (full-stack) | Implementing a data architecture on Fabric, ingesting from source systems, building batch/real-time ETL/ELT pipelines, modeling a Lakehouse/Warehouse, or handling Eventstream/Eventhouse. |
| `@joseph` | DQ / DataOps Engineer | Introducing or extending data quality rules, defining SLOs/data contracts, investigating suspicious report numbers via lineage/freshness RCA, or hardening DataOps practices. |
| `@kent` | QA / Test Engineer Data | Setting up a project's test strategy, adding unit/regression tests for notebooks or semantic models, load-testing Fabric capacity before a release, or investigating DAX/KPI regressions. |
| `@cole` | UX Data Designer | Executive/client-ready reports, WCAG accessibility compliance, custom Power BI visuals when standard visuals aren't enough, or Power BI Embedded / design system / theme work. |
| `@mike` | FinOps Advisor (part-time) | Project kickoff cost review, periodic Fabric/Azure cost reviews, capacity/SKU audits, chargeback model definition, or responding to cost spikes/anomalies. |

**Invocation**: either `@name`-mention an agent directly (e.g. `@ralph
design a Bronze/Silver/Gold layout for Sales`), or just describe the task
and let Copilot auto-select the right one — every agent's `description`
carries trigger phrasing for exactly this.

**Recommended hand-off order** (a default, not a hard rule — skip or
reorder stages a task doesn't need): `@karl` (requirements) → `@ralph`
(architecture) → `@reza` (build) → `@marco` (model/report) →
`@kent`/`@joseph` (test/quality) → `@cole` (UX polish), with `@mike`
advising on cost throughout. `@dave` and `@ada` are meta-roles for
maintaining this agent roster itself, not for Power BI/Fabric delivery
work.

**When it's unclear which agent fits**: if a request matches more than one
agent's description equally well, or none clearly, ask the human which
persona to engage rather than silently guessing — the same "never guess"
discipline used for release version bumps above.
